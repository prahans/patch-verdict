# PatchVerdict Mission Control

Mission Control is the local hackathon UI for PatchVerdict.

The home page can now start the existing PatchVerdict backend workflow. The web
app does not reimplement investigation, patching, verification, or verdict logic.

```text
Browser form
  → POST /api/missions
  → src/real-mission-demo.ts
  → PatchVerdict backend + E2B sandbox
  → output/<missionId>/ proof bundle
  → /missions/<missionId>
```

The proof bundle remains the boundary between backend execution and the mission
detail UI. Verdicts are generated by the backend and only displayed by the
frontend.

## Run locally

Install the repository dependencies first, including the root backend
dependencies and the web app dependencies.

From `apps/web`:

```sh
pnpm dev
```

Open http://localhost:3000.

The mission form includes the current Vitest cleanup benchmark as demo defaults.
Change the repository, issue, reproduction command, or required failure text as
needed and click **Run PatchVerdict**.

The request runs on the Next.js Node server and may take a while because it
creates a sandbox, installs/prepares the target repository, investigates,
patches, verifies, and writes the proof bundle. When the backend prints the new
Mission ID, the browser redirects to the matching mission page automatically.

The root `.env` must contain the backend credentials used by PatchVerdict,
including `OPENROUTER_API_KEY` and the E2B configuration required by the
existing backend.

## Data boundary

`proof.json` and `events.json` → server-only `loadProofBundle()` →
`MissionViewModel` → mission UI components.

The frontend does not calculate a verdict and does not trust form input as
evidence. It launches the existing backend and then reads the serialized proof
artifacts that backend produced.

Required bundle files:

- `proof.json`
- `events.json`

Optional files:

- `investigation.md`
- `patch.diff`
- `evidence/baseline-test.json`
- `evidence/post-patch-test.json`
- `evidence/full-suite.json`

## Local-only bridge

The `/api/missions` route is intentionally a local hackathon bridge. It starts
`src/real-mission-demo.ts` through the repository's installed `tsx` CLI and
waits for the backend to print a Mission ID.

Do not deploy this route as a public arbitrary-code execution service. For a
real hosted product, mission execution should move behind an authenticated job
queue/service boundary.
